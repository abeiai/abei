# abei 旧版数据只读导出方案

日期：2026-10-02，2026-10-08 补充旧后台四类日志迁移要求。状态：方案设计完成，尚未执行线上数据盘点、导出或导入。

## 1. 结论与本次边界

建议采用“独立只读采集器 → 加密原始导出包 → 本地校验及转换 → 新版隔离库演练”的方式。先完整保留用户、创作内容、素材引用、交易和未履约权益，再决定哪些数据进入新版业务表。没有对应结构的数据列为后续开发要求，不丢弃、不强行转换。

本次只检查本地旧版源码、配置项及新版数据模型，只新增本方案文档。没有连接旧版数据库、Redis、对象存储或应用接口；没有读取线上业务记录，也没有执行线上写操作。

| 项目 | 本次范围 |
| --- | --- |
| 允许修改 | `docs/`，仅本方案 |
| 不修改 | `abeiai/`、`apps/`、`packages/`、部署脚本、环境文件、数据库及云资源 |
| 交付 | 数据清单、只读访问约束、导出包协议、映射规则、缺失结构及实施验收条件 |

| 数据库 migration / seed | 本次均不需要；下文新增结构须在后续独立开发任务中完成 |

以下“已确认”均指本地资料所能证明的事实。线上版本、真实表结构、记录数、权限、存储引擎、文件体积和实际数据质量均待只读盘点，不能把本地模型当作线上数据库已经核实的结果。

## 3. 只读访问设计

### 3.1 数据源和权限

1. 优先使用**已有**的只读副本或已有只读账号。当前 env 中账号的有效权限未知，账号名称不是只读证明。
2. 来源明确区分 `legacy-base` 和 `legacy-dev-overlay`；生产候选配置从 `base.env` 提取，但仍须通过数据库身份、已批准的库名/地址和版本核验，不能仅凭文件名认定为生产。
3. 只读盘点包括 `SELECT VERSION(), DATABASE(), CURRENT_USER()`、`SHOW GRANTS`、角色的有效权限（若适用），以及 `information_schema` 的表、列、主键、外键、索引和引擎元数据。盘点结果中的地址、账号、授权文本仅在受限本地保存，公开报告脱敏。
4. 数据账号只应具有选定业务表的 `SELECT` 和必要元数据读取权限。若已有权限不能证明无写能力，停止线上采集；不得通过“尝试写入再回滚”验证权限。
5. 缺少只读账号/存储凭据属于执行前置条件。**本任务不执行 `CREATE USER`、`GRANT`、`REVOKE`、云权限调整或任何线上配置变更。**
6. OSS/R2 使用已有、限定 Bucket/前缀的读取凭据，仅允许列举对象、读取元数据和下载对象。版本对象或 KMS 加密对象需要相应既有读取/解密权限，缺失时报告访问缺口，不修改权限或加密设置。

OSS 的列表权限可限制前缀，对象读取权限可限制对象范围；下载指定版本还需要版本读取权限。依据：[OSS 目录权限](https://www.alibabacloud.com/help/en/oss/user-guide/access-control-base-on-ram-policy)、[GetObject 权限](https://www.alibabacloud.com/help/en/oss/developer-reference/getobject)。

### 3.2 采集器的硬限制

- 使用独立 MySQL 驱动和直接存储读取客户端。禁止启动 Django、导入其业务模块、运行 `manage.py`、复用存储后端、调用应用页面/API、触发短信/邮件/支付/AI请求。
- SQL 使用预先审查的固定模板及参数绑定；表名/列名来自核验过的白名单，禁止任意 SQL 参数入口。只允许纯读取 `SELECT`、必要的元数据 `SHOW` 和下述会话/事务控制。
- 禁止所有 DML/DDL、存储过程和自定义函数、临时表写入、`SELECT ... INTO OUTFILE/DUMPFILE`、显式锁表、`FOR UPDATE`、`FOR SHARE`、`FLUSH` 和全局设置。
- 不读取、导出或操作 Redis。会话、验证码、在线状态和任务队列不作为新版恢复目标；新版会话独立生成。
- 对旧存储禁止上传、删除、复制对象、修改 ACL、创建 Bucket、修改生命周期和任何“下载后上传回源站”的封装方法。
- 日志只输出批次、表名、数量和错误类别，不能输出连接串、密码哈希、手机号、提现账号、完整 URL 签名或作品正文。
- 数据只流向本地专用加密目录，例如仓库内已忽略的 `backups/legacy-export/<run-id>/`。目录权限 0700，文件权限 0600；密钥由单独安全渠道提供，不能和导出包一起保存。
- 采集器不接收新版数据库连接串。后续导入器只读取导出包、只连接 abei 专属目标库；不得把源库和目标库放进同一个可写运行进程。

### 3.3 一致性快照

先检查实际 MySQL 兼容版本与全部必需表的存储引擎。如果是经核验支持此语义的 MySQL/InnoDB，核心业务表和其关系表在**同一连接、同一只读事务**中采集。以下是未来采集器的会话设计示意，本次未执行：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY;
-- 固定白名单表和列的普通 SELECT；在同一连接中分批读取。
ROLLBACK;
```

`SET SESSION` 只调整当前连接，不修改线上业务数据或全局配置。`READ ONLY` 不是唯一防线：MySQL 仍允许某些临时表操作，因此必须同时依赖有效只读权限和 SQL 白名单。快照依赖 InnoDB 和 `REPEATABLE READ`，依据：[MySQL 事务文档](https://dev.mysql.com/doc/refman/8.0/en/commit.html)。

- 表结构在采集前后计算本地签名；发生并发 DDL、表缺失或必需列不符则整批失败，不能静默删列继续。
- 多连接各自建立快照不等于全局同一时刻，不能把并行表导出声明为一个一致性快照。
- 非事务表、兼容数据库、列存实现或无法验证快照语义时，停止“强一致导出”路径；优先读取已有稳定副本/备份。不得为此在线修改引擎、加锁或创建备份。
- 长事务会增加源端压力，普通查询也可能持有元数据锁。数据库阶段先集中读取、尽快结束，素材下载和转换在事务结束后处理；不能承诺零性能影响。
- 读取副本时记录已有的复制进度/延迟证据；副本尚未追上发布截止点时，不能视为最终导出。

3. 抽象模型没有独立物理表，但字段在实际子表中；所有隐式 ManyToMany 中间表都要纳入。无自增 ID 的关系表按已核验的复合主键/唯一键读取，不猜测表名或排序键。
4. 发现清单外的真实业务表或迁移记录与本地源码不一致时，登记差异并分类后再运行，不能默认忽略。

## 5. 关键字段与转换规则

### 5.1 用户、登录和权限

用户主包至少包含 `id/username/email/nickname/avatar/is_active/date_joined/last_login/msg_id`，微信身份、公司归属、推荐关系、会员到期日、两类余额及扩展业务字段。`first_name/last_name` 按用途保存，用户标签单独导出；注册 IP 等字段置于受限辅助包，避免不必要地进入新版用户展示。

- 主键采用 `(sourceSystem, sourceTable, sourcePk)`；旧 BigAutoField ID 一律十进制字符串。`msg_id` 只作辅助追溯，不是全库或单表唯一性的替代证明。
- 用户和新版 ID 用映射表关联，新版 `accountNumber` 独立分配，不把旧 ID 当作新版账户号。重复运行复用已生成目标 ID。
- 不只按手机号或邮箱自动合并。核验来源、空值/重复情况、企业账号、同一人多个账号及已有新版账号；冲突进入人工处理清单，保持作品和权益原归属。
- 旧 `username` 可能是手机号、空值或企业名。手机号需规范化；旧字段不证明手机号已验证，不能自动设置 `phoneVerifiedAt`。
- 空邮箱不允许共享同一个空字符串或杜撰“已验证邮箱”。可复用新版内部占位邮箱机制；无手机号的微信/企业账号需要唯一内部身份和不可发信规则，或后续调整邮箱结构。占位邮箱不能成为通知、找回密码或身份验证的投递目标。
- 微信 `openid/xcx_openid/unionid` 保留来源 AppID/平台上下文；只有确认同一应用身份空间后才映射到新版相应字段。更换 AppID 时不能直接认定可登录。
- 密码哈希在**独立加密凭证包**保存，限定导入权限，禁止进入主包、日志和 UI。旧算法分布需只读统计：`pbkdf2_sha256` 等只是候选，尚未核实线上算法。
- 推荐开发旧哈希安全验证器：支持经过确认的算法与参数上限；首次成功登录仅在**新版**转换为 scrypt。不支持/不可用哈希走经验证的新版找回流程；禁止破解密码、统一初始密码或只把 Django 哈希塞入现有校验器。
- 旧 `is_staff/is_superuser/groups/user_permissions` 不赋予新版管理员权限。旧后台账号单独清点，`AdminUser` 通过独立明确流程建立，不能把用户迁移当作权限授权。

### 5.2 作品和绘本

`Product.result`、`Works.result`、任务 `request/response/extra` 保留原始 JSON 及结构版本，不能只保留标题和一个输出 URL。`Product.category_id`、模板 ID 来自真实数据和映射表，不硬编码分类编号。

旧版绘本生成代码中存在 `result[] → rn_case_pages[]` 的布局：[旧绘本结果构造](../abeiai/abei-backend-main/app_ai/one_take/book.py)。新版页结构为 `position/caption/imagePrompt/narration/imageUrl/audioUrl/...`：[新版绘本页协议](../apps/api-core/src/picture-books/picture-book-plan.ts)。建议转换如下：

| 旧字段 | 新版候选字段 | 规则 |
| --- | --- | --- |
| `Product.user_id` | `PictureBook.userId` | 经身份映射，不从嵌套结果中的用户显示对象推断归属 |
| `Product.title` / `result[].title_zh` | `title` | 保留原值和选取依据 |
| `img_cover`、封面中文音频 | `pages[0]` | `position=0`；封底另归档，不伪造为正文 |
| `rn_case_pages`、`app_cms.Pages` | `pages[1..n]` | 按旧 `sort,id` 稳定排序；`pageCount` 为正文页数 |
| `body_zh` | `caption/narration` | 中文可见正文及朗读文本；区别其他语言内容，原包完整保留 |
| `img/audio_zh` | `imageUrl/audioUrl` | 经素材映射替换地址，缺失时明确显示缺失 |
| 原画面提示词 | `imagePrompt` | 有则迁移；没有则不得生成虚构提示词以通过完成校验 |
| 原生成任务引用 | 任务 ID 字段/历史关联 | 只引用真正导入成功的任务；其余保留源 ID，不能填旧 ID 当新 FK |

新版当前完成校验要求每页展示文字和画面提示词：[绘本服务](../apps/api-core/src/picture-books/picture-book.service.ts)。因此已有旧绘本可能能播放但不能直接进入现有完成/编辑流程，需要“历史作品查看”或兼容导入状态。其他故事、脚本、图片、朗读、视频、数字人等应先进入通用历史作品结构，不能全部塞进 `PictureBook`、`Article` 或 `AiTask`。

公开广场副本、审核记录和私人原作品分别保存。保留 `is_delete/is_show/is_active/is_license`、分享密码/访问范围及旧链接映射；分享密码只在受限加密区域保存，未来承接时使用安全校验结构。未审核、停用、删除或私人记录默认不公开。旧 HTML、模板和外链作为数据保存，展示前做安全过滤，禁止执行旧模板脚本。

### 5.3 订单、余额与待释放权益

旧模型中的 `ProductOrder` 实际是企业产品授权，字段缺少收款订单号/金额/支付交易号，不能直接当作新版 `EnterpriseOrder`。`app_open.Recharge` 是开放平台充值记录，不能默认归到某个前台用户。

| 旧字段 | 新版候选 | 规则 |
| --- | --- | --- |
| `MemberOrder.order_id` | `PaymentOrder.orderNo` / 历史订单号 | 保留原号，按来源命名空间检测碰撞 |
| `pay_price` | `amountCny` | Decimal 字符串或整数分处理，禁止二进制浮点转换 |
| `order_mode=0/1` | `WECHAT_PAY/ALIPAY` | 来自旧设置；支付渠道不是 `pay_type` |
| `pay_type=1/2/5` | 小程序 / JSAPI / 主扫 | 新版缺少微信小程序支付枚举，历史记录保留原方式，不冒充桌面/H5 |
| `order_status` | 历史已完成/未完成标志 | `false` 无法区分 CREATED/FAILED/CLOSED；`true` 也可能是赠送，不直接证明收款 |
| `pay_id/pay_time` | 交易号/收款时间 | 保留空值和异常；不按订单时间补造支付时间 |
| `is_bonus` | 赠送来源 | 赠送订单与真实收入分开，不能伪装成支付宝/微信已收款订单 |
| `member_time=0/1` | 月 / 年 | 保留原期限，不能按统一天数重建全部历史 |
| `User.point`、`User.bonus` | 购买点数 / 历史赠送点数 | 分别核对；不默认合并、不预设贝壳与新版点数汇率 |
| `PointPlan.point/push_date/status` | 待释放计划 | 全部导出，分别统计源端标记已释放/未释放、未来及逾期计划；两个状态值都不能单独证明实际到账或未到账 |

默认建议：先建立只读历史订单档案及迁移权益结构，不直接把全部旧订单放入正常支付状态机。后续如承接到 `PaymentOrder`，必须先加入来源/历史标志并在支付查询、通知结算和权益发放处隔离历史订单；禁止创建新支付、重放回调、补发充值或发送用户通知。

旧订单没有完整权益快照，点数流水也没有订单外键；当前 `MemberLevel/PointLevel` 配置不一定等于购买当时配置。不能仅由金额或现价倒推出历史到账数量。无法证实的数据记录 `unknown` 和依据缺口，不能填 0 表示“已知为零”。

余额对账在同一数据库快照内执行：

```text
购买余额快照 = User.point
赠送余额快照 = User.bonus
购买流水净额 = SUM(PointHistory.point WHERE is_bonus = false)
赠送流水净额 = SUM(PointHistory.point WHERE is_bonus = true)
每用户差异 = 余额快照 - 对应流水净额
```

任一差异、负余额、超出新版 Int 范围或缺失用户先进入异常清单。采集器不修正源数据。后续初始化新版余额采用已批准的快照与换算政策，历史流水单独展示，迁移开户账只记一次；不能“回放历史流水后再加余额快照”。已导入批次重复执行应产生零新增余额/权益。

新版钱包存购买点数，会员期限另有 `remainingCredits`：[个人点数处理](../apps/api-core/src/wallet/personal-credits.ts)。但旧 `bonus` 混合会员释放和其他奖励，不能整体认定为一个新版会员周期。`PointPlan` 缺少订单外键；新版 `MembershipPeriod` 必须关联订单且 `orderId` 唯一，也不能直接表示旧订单的多个按月释放计划。需要独立迁移权益/释放模型，保留当前到期日、余额和未释放承诺，避免重复发放。是否换算、过期及使用优先级是发布前业务决策，不能由导出程序自行决定。

**数据库快照一致，不等于旧业务操作已经完成。**旧 `action_point_plan` 先通过 `save_point` 写流水/余额，再保存 `PointPlan.status=true`，本地代码在这段流程中没有显式事务包裹；订单的 `post_save` 也逐步生成会员历史和计划。因此快照可能同时包含“点数已到账”和“计划仍为 false”，即使余额与流水已经对平，按计划标志继续发放仍会重复。反向也有风险：`save_point` 对有效企业授权账号可能直接返回而不写个人点数流水，写流水失败也会返回失败，但释放函数未检查返回结果，仍可能置 `status=true`。所以 `true` 同样不能单独证明实际到账。该问题依据：[旧点数释放流程](../abeiai/abei-backend-main/app_user/apis.py)、[订单保存信号](../abeiai/abei-backend-main/app_user/single.py)；线上外围事务设置仍待核验。

所有释放计划必须增加承接核对状态：先为 `unverified`，核对后分别记录实际已到账、尚未到账、旧企业授权规则适用或仍有歧义及相应证据；只有已确认需履约且未到账的计划才转为可执行。按用户、释放日期、流水时间/金额/描述和最终快照寻找对应记录只能生成候选证据，旧流水没有计划外键，不能据此自动认定一一对应。多笔同额、重复计划、执行中窗口或缺乏唯一证据时保持暂停并进入受限异常清单；订单的已发权益/计划也需要交叉核对。最终切换必须解决执行中的旧发放流程，再核对一次；导出器不在源端修正状态，新版不依据 `false` 直接自动发放，也不依据 `true` 直接认定履约完成或豁免补发。

分销佣金和提现是人民币负债，不是 AI 点数。提现收款账户、姓名和手机号放在权限更窄的独立加密财务包；不得初始化到个人 AI 钱包、重发提现或重算旧分销收益。

### 5.4 旧后台四类日志

对话、图片、语音和视频日志均为 **P0 必迁数据**，包括成功、失败、进行中、无输出和用户关联为空的记录，不按后台当前筛选条件或分页范围截取。旧后台分别通过 `chat/draw/tts/video/admin/message/data` 展示数据库记录：[日志路由](../abeiai/abei-backend-main/app_ai/urls.py)、[列表及详情序列化器](../abeiai/abei-backend-main/app_ai/admin.py)。采集仍直接读取已核验的数据库表，不调用这些后台接口；序列化器仅用于核对旧页面展示了哪些字段，不能代替完整字段清单。

| 类型 | 源模型及归属 | 必须保存的详情与依赖 |
| --- | --- | --- |
| 对话 | `ChatMessage → ChatSubject.user`；工作空间通过 `ChatSubject.workspace` 关联 | 用户输入、AI 回复、系统提示词、主题及消息顺序、请求/响应时间、状态、错误、tokens/输入输出长度、`extra`；关联 `LLmVersion/LLmModel`、工作空间与模板。按主题内旧消息 `id` 升序恢复对话，不只导入列表摘要 |
| 图片 | `DrawMessage.user` | 原始/中文/英文提示词、负面提示词、`results` 全部图片及顺序、输入图、角色/风格/内容参考图、比例、风格、构图、模式、seed、n、相似度、`api_id`、`retry`、状态、错误、时间和 `extra`；关联 `DrawVersion/DrawModel/DrawStyle/DrawComposition` |
| 语音 | `TtsMessage.user`；`TtsSubject.user` 为独立的多轮语音记录 | 合成文本、输出音频、文本长度、时长、音色版本、时间、状态、错误、`retry` 和 `extra`；多轮语音另保留 `body`、合成结果及其实际引用的分段消息/音频，不假定存在消息外键；关联 `TtsVersion/TtsModel` 及音色字典 |
| 视频 | `VideoMessage.user` | 用户输入、输出视频、宽高比、模型版本、远端 `task_id`、时长、时间、状态、错误、`retry` 和完整 `extra` 中的业务参数及素材引用；关联 `VideoVersion/VideoModel`，包括实际引用的输入图片、首尾帧和封面 |

字段依据：[旧消息模型](../abeiai/abei-backend-main/app_ai/models.py)。每条记录保留旧主键、`msg_id`、来源表及原始关联 ID；`msg_id` 在源码中只有索引，不能代替 `(sourceSystem, sourceTable, sourcePk)` 唯一键。助手的 `BotsSubject/BotsMessage` 以及数字人 `HumanMessage` 已在其他创作记录中纳入，不因四类后台菜单而排除。

多轮语音的关联证据藏在 `TtsSubject.body[]` 的 `msg_id/version_id/hash_str` 和 `TtsMessage.extra.subject_id` 中，[旧语音保存逻辑](../abeiai/abei-backend-main/app_ai/single.py) 存在按 `msg_id/hash_str` 尝试复用成功分段的分支；实际关联和复用情况以导出记录核验。保留 `body[]` 顺序与这些关联证据，会话与分段采用有序明细关系，允许一条分段被多个会话引用。`msg_id` 重复、引用不存在或会话与分段用户不一致时隔离待核验，不能任取一条或通过会话引用开放其他用户的音频；`extra.subject_id` 也不能作为唯一父关系覆盖复用记录。

转换和导入要求：

1. 旧状态原值与标签同时保留：`0=用户已请求`、`1=机器人回复中`、`2=机器人回复完成`、`3=系统错误`、`4=数据传递中`，依据 [旧状态字典](../abeiai/abei-backend-main/abei/settings.py)。归档层可提供等待、处理中、成功、失败、未知的查询标签；旧进行中记录不入新任务队列，不自动重试、轮询远端、执行回调或续跑。快照之后发生的状态变化由最终补导核对。
2. 用户通过已有迁移映射关联；对话以主题的用户为来源归属。空用户、缺失主题或关联冲突保留为归属待核验档案，只允许具有历史日志访问权限的管理员查看，不分配给测试账号、不自动向普通用户公开。工作空间或 `extra` 内的用户标识仅用于交叉核对，不能覆盖可信归属。
3. `extra.config.template` 和 `extra.V` 等旧后台“应用/版本”展示来源保留业务元数据。模型、模板、音色停用或删除不导致日志丢弃；能核实的名称和版本作历史快照，缺失时保留旧 ID 并显示未知，不套用新版当前模型或当前价格。依赖字典仍排除 `api_key`、授权头、连接配置和其他凭据。
4. 时长和 tokens/长度保留源值及口径证据。音频/视频时长在核验提供商写入逻辑前不统一换算；模型默认的 `0` 不证明实际零用量。没有旧扣点/成本的可靠关联时标记未知，不能按 tokens、当前价格或重试标志重算，也不能构造实际调用次数。
5. 图片、音频、视频以及输入/参考素材进入第 6 节同一素材清单，保存记录、字段路径、数组位置和输入/输出角色。素材共用实体可以去重，日志记录与引用不能去重掉。输出已失效或下载失败时保留原日志与缺失说明，不把“旧生成成功”改成“生成失败”，也不请求重新生成。
6. 全文和原始业务 JSON 在受限加密档案中保存；解析、扫描疑似密钥后再生成后台可展示版本，凭据分离且不进入页面。用户正文、系统提示词和错误信息可能包含私人内容，列表使用脱敏摘要，详情按权限查询；HTML/Markdown 展示需要过滤，不能执行旧脚本。后台日志的日期格式有省略年份的情况，迁移必须读取数据库原时间，按上海时区转换，不解析显示字符串。

新版 [AiTask/AiCallLog/AudioTask/AudioUsageLog](../packages/database/prisma/schema.prisma) 仅部分对应。`AiCallLog` 记录调用用量和结果元数据，没有完整输入、输出及会话字段；`AiTask` 要求新版用户和场景，`AudioTask/AudioUsageLog` 关联新任务与结算，均没有完整旧来源/会话结构。默认新增独立历史归档，不把旧记录直接塞入当前执行/结算表；旧历史量也不能混入新版实时调用量、成本、失败告警和扣点统计。新版 `AudioDialogueProject` 是语音创作项目，不能等同于聊天主题或旧 `TtsSubject`。

归档最小结构列入第 9 节：`LegacyAiSession` 保存主题/工作空间和可核验用户，`LegacyAiLog` 保存四类记录、来源唯一键、状态、正文/业务参数、历史版本及未知用量，`LegacyAiSessionItem` 保存会话中的顺序及消息引用，`LegacyAiLogAsset` 保存有序素材引用。单条图片/语音/视频日志允许没有会话；关联用户允许为空。源 PK、原始字段及关联仍在加密导出包中保留，归档模型的名称在实现时确定。

后台需新增“历史 AI 日志”入口，提供对话、图片、语音、视频四个筛选类别；按来源用户、时间、状态、模型/版本、应用和旧记录 ID 查询，详情支持完整对话、图片组预览、音频/视频播放及缺失提示。可从现有 `/admin/ai-tasks`、`/admin/audio/tasks` 导航进入，查询历史数据时使用独立数据源和权限。迁入历史日志不要求复刻旧后台编辑、删除、重试或执行功能。

## 6. 素材采集

数据库快照结束后，从本地导出内容生成素材清单，再下载实体文件。需要遍历 URL/File/Image 字段、JSON 的所有层级、HTML/Markdown 的媒体引用，以及生成图片数组、PDF、视频、封面、头像、音频、文档和反馈附件。URL 字段和嵌套 JSON 均需保存引用位置，不能只用顶层 URL 正则。

每项至少记录：`sourceTable/sourcePk/fieldPath/ownerScope/ownerId/originalUrl/storageProvider/bucket/objectKey/versionId/etag/lastModified/sizeBytes/mimeType/localBlobHash/downloadStatus/consistencyStatus/errorCategory`。完整 URL、原对象标识和访问参数属于受限导出包；公开报告只给数量和脱敏来源。

- 对 OSS/R2 自有对象用对象读取接口，优先基于已核验域名、Bucket 和前缀解析 objectKey。FileField 的相对路径通过已核验的旧存储位置解析，不调用旧 Django storage；避免重复添加 `MEDIA_URL` 或错误解码中文路径。
- 必须覆盖主 OSS、旧代码中的第二个 OSS Bucket、实际引用的 R2 和其他素材来源；env 没有提供的凭据列为缺口。
- 对象下载优先固定现有 versionId；未开启版本时用 ETag 条件读取，并记录下载前后元数据。被覆盖/删除的对象不能凭数据库事务恢复，必须报告 `changed/missing`，不能修改源版本或生命周期。
- 数据库快照和对象存储没有共同事务。快照后才取得的 ETag/versionId 只证明下载时的对象身份，无法排除“快照后覆盖、首次 HEAD 前已稳定”的情况。只有旧行中已固定的版本/内容哈希、经证实不可变的对象键，或另行授权切换后的稳定来源证据，才能支持相应一致性结论；不能把首次下载得到的版本当成旧行已固定版本。缺少证据时标记 `download-time-only`，单列数量及用户影响，不能计为 `snapshot-verified` 或宣称整包素材与数据库快照完全一致。
- ETag 不一定等于文件 MD5，不能拿它当本地完整性哈希；本地流式计算 SHA-256。相同文件可以去重，用户/企业/作品引用和授权关系不能去重掉。
- 第三方临时 URL 只在有效期内读取；过期则报告。不得触发重新生成、转码、续签业务流程或付费接口来“补齐”。外部知识库仅归档数据库已有正文/源文件和外部 ID；不能声称已备份远端全文/向量。额外第三方读取要先确认接口没有写副作用及可用的只读权限。
- 下载白名单只包含经过核验的纯对象存储/CDN来源；逐跳检查重定向及 DNS/地址，禁止访问旧站应用页面/API、云元数据、内网地址或携带源凭据转发到其他域名。未知 URL 进入人工分类清单，不因 HTTP 方法是 GET 就自动访问。
- 一个文件一次流式读取，限制最大尺寸、超时和重试次数。初始数据库批次建议 500 行、素材并发 2，体积大则减小；实际吞吐/带宽/事务时长预算通过预检决定，不宣称这些参数已压测。
- 导出只写本地文件。后续上传到新版 abei 自有存储属于另一阶段；不能上传回旧 Bucket，不能复用 xueleai 资源。README 所述新版绘本 R2 存储可作为后续目标候选：[abei 说明](../README.md)。

## 7. 导出包协议

建议目录（逻辑名称，文件均在本地加密保存）：

```text
backups/legacy-export/<run-id>/
  manifest.json.enc           来源指纹、版本、快照、覆盖范围、完成状态
  schema.json.enc             实际列/类型/关系/引擎及与源码的差异
  tables/<source-table>.<chunk>.ndjson.gz.enc
  relations/<source-table>.<chunk>.ndjson.gz.enc
  credentials/users.ndjson.gz.enc
  finance/withdrawals.ndjson.gz.enc
  assets/index.ndjson.gz.enc  素材及引用清单
  blobs/<sha256>.enc          文件实体
  checkpoints/*.json.enc      本地进度，不写回源库
  reports/*.json.enc          行数、断链、权益、订单、素材异常
```

原始业务行使用 `{sourceSystem, sourceTable, sourcePk, values}` 封装，保留原始字段名、空值及关系 ID，schema 另存字段类型。认证哈希、提现信息等只在对应受限包保存，主包仅保留关联 ID，不重复散布敏感字段。

序列化必须无损：整数 ID/超出安全范围整数和 Decimal 用字符串；时间同时保留原始本地值、来源时区及转换后的 UTC；DateField 到期日不自动当成 UTC 零点。明确业务有效期是否包含到期当日，再转换为半开区间。JSON 数组顺序、换行、Unicode 和空对象/空数组不得改变；不要用 JavaScript Number 解析未知精度数值。嵌套 JSON 的大整数/小数也保留精度，必要时保存原始 JSON 文本。

表/列采用明确白名单，不使用 `SELECT *`。在配置、请求、结果或 `extra` 中发现疑似 token/secret/授权头时，标记并分离凭据或进入受限待审区；不能因为顶层字段排除了 `api_key` 就认为嵌套内容安全，也不能用全局替换破坏用户正文。

manifest 包含：

- 协议版本、唯一 `runId`、来源命名空间及脱敏指纹、源库/源码版本证据、时区、开始/结束时间、快照建立方式和副本进度（如有）。
- 每表选取列、筛选政策、引擎、主键、行数/主键范围、批次和校验和；每个分片记录内容哈希及加密后文件哈希，明确不同哈希的范围。
- 必需/辅助覆盖状态、原始数据与凭证包位置、被排除列、缺失表/列/文件及来源差异。存在例外不得标记为“完整可发布”。
- 四类后台日志分别统计记录数、状态数、用户/主题关联异常、输入/输出素材引用数及读取结果；包含无主、失败和进行中记录，不能只给一个成功任务总数。
- 进度按 `data_snapshot_complete/assets_complete/validation_passed` 分开，最后才写包完成标记。只有采集和校验结束的包可进入演练。

同一只读连接中的每表用主键游标分页，例如 `id > last_id AND id <= snapshot_max_id ORDER BY id LIMIT batch_size`；主键上限在同一事务中取得。无合适键时先确定稳定读取策略，不能用巨大 OFFSET 掩盖问题。

**数据库连接断开会失去快照。**重连后不能从旧 checkpoint 继续并声称还是同一快照；必须开始新 run，重采全部核心表/关系表。素材下载可按已完成数据库包独立续传，版本/哈希不符重新验证。未完成数据库包禁止导入。

## 8. 实施顺序和发布前补导

### 阶段 A：只读预检

核验数据源、有效权限、版本/引擎、真实表结构、依赖中间表、必要字段和现有副本状态。`information_schema.TABLE_ROWS` 仅作容量估计，精确行数以快照中流式读取计数为准；关键财务表的 COUNT/SUM 在同一快照内复核，避免重复全表扫描。

输出用户总数及身份冲突类别、各业务表覆盖情况、点数/会员/订单/提现异常、素材来源与访问缺口。线上盘点若会扫描大表，先根据索引和容量缩小读取压力，不运行维护或优化命令。

### 阶段 B：全量只读导出

按依赖顺序采集字典、用户、企业关系、作品/文档、订单/权益、创作历史、公开内容、关系表。全部核心关系在一个可验证快照中完成；随后生成素材清单、下载文件、校验包并保留加密副本。

### 阶段 C：离线转换及新版演练

只使用导出包，不回连旧服务。先补齐下文 P0 结构及导入安全隔离，再在 abei 专属演练库导入：身份映射 → 用户/归属 → 私人内容/素材 → 四类历史日志/会话及素材引用 → 历史订单 → 余额/权益 → 公开内容。检查页面可见结果、权限、幂等和财务守恒。

本项目遵守 `abei` Compose/专属卷和 3600–3680 端口段；需要本地入口/数据库时使用 3600/3604。不得沿用上游发布脚本连接 xueleai 线上、3320 端口段或其容器/卷。旧库远端既有端口仅作为明确核验的外部来源，不在本项目新增同端口服务。

### 阶段 D：发布前最终导出与对账

仅按 `id > last_id` 或创建时间补导是不充分的：旧用户、会员订单、`PointPlan` 和不少关系表缺少可靠更新时间；已有 ID 的付款、余额、解绑、关系删除和内容修改都可能漏掉。

默认采用第二次完整快照，并在本地比较主键集合和规范化业务行哈希，形成新增/修改/删除差异。带更新时间的表可用于中间预同步，但最终仍对核心表和关系全集核对；删除识别必须是同范围完整扫描，不能把缺失分页当删除。素材按版本/哈希复用和补读。

**目前“完全只读采集”无法单独保证最终切换零遗漏。**旧系统在最后快照后仍可注册、支付、扣点、完成任务和修改作品。现有资料没有证明已有 CDC 或业务冻结机制：

- 本任务不停止服务、不修改旧站配置、不关闭定时任务、不建立触发器、不调整 binlog、不创建复制链路。
- 正式切换前需要另一个经过明确授权的发布任务处理所有旧写入者（支付回调、后台、定时释放、AI异步任务和旧入口），或接入已经存在且获准读取的完整变化记录；只冻结前台不足以保证一致。
- 若继续保持本任务的纯只读边界，就只能交付带明确截止点及未同步风险的快照，不能宣称“截至上线时所有数据无损迁移”。
- 待支付订单、进行中任务、逾期未释放计划要有责任归属和交接清单。不能为了补齐而在旧端结算/执行，也不能在两端同时发放/扣款。

## 10. 验收与回退

导出阶段的发布门槛：

1. 有效权限和采集代码证明只读；执行记录中没有应用 API、业务写入、源端配置变更、显式锁或源文件上传/删除。不得通过线上故意写入来证明只读。
2. 每张必需表满足 `快照读取数量 = 完成分片数量之和`，主键不重复、分片哈希正确；每项缺表、断链、归属不明和结构差异有明细。
3. 每用户两类余额、所有释放计划、会员到期日核对完成；计划标志与实际到账之间的双向差异有明确处置，不能仅凭余额对平或 `status=false` 开启发放，也不能仅凭 `status=true` 忽略未履约权益；订单按渠道/赠送标志/状态分组统计数量与金额；分销余额、收益及提现分别对账。差异未解释时不得激活新版权益。
4. 必需素材的每项引用均有成功读取的实体哈希或明确缺失记录，下载成功与快照版本一致分别统计。标记缺失或 `download-time-only` 不算快照完整；素材访问/版本证据缺口、第三方远端缺口及其用户影响经处理后才能发布。
5. 时间、金额、BigInt、JSON及外键转换通过本地样本验真，覆盖空手机号/空邮箱、重复身份、非 scrypt 哈希、软删除、失败任务、赠送订单、午夜到期日和嵌套素材。
6. 导出包及凭证包可在独立本地目录解密校验；正文/手机号/凭据不出现在公开报告、Git、部署包或终端日志。

后续导入验收：同包导入两次，第二次无新增用户/订单/作品/余额/发放；历史订单不能触发支付结算；未来计划只发一次；私人内容不能跨用户/企业访问；不创建旧管理员权限；旧素材经过新归属授权仍能查看。页面验收优先复用现有账号、`/picture-books`、`/voice`、用户历史/余额和 `/admin/payments`，缺失页面另列开发任务。

四类日志专项验收：按源表/状态对账 `导出记录 = 已导入记录 + 有明细的隔离待处理记录`；失败、无主和进行中记录不得静默遗漏，待处理部分不能宣称已导入可用。抽查完整对话顺序和系统提示词、图片多结果及参考图、语音文本/音色/音频、视频输入/时长/视频文件、历史时间与错误；失效素材显示缺失。相同包二次导入时日志、会话和素材引用数量不变；钱包、当前任务队列、实时用量统计不因历史日志导入变化；后台未登录访问被拒绝，普通用户不能访问他人的日志或素材。后台历史日志页面必须实际验收，原包备份不等于后台导入完成。

导出器测试只用本地假连接/临时数据，验证禁止 SQL/API 被拒绝、快照重连失败、分片损坏、URL重定向、缺失对象、快照后覆盖但 HEAD/GET 稳定的对象、已到账但计划为 false、未到账但计划为 true 的状态以及敏感日志等情况。只有实际实现后才增加可执行验收命令，本次不声称存在导出脚本或测试。

回退只针对新版隔离导入批次/演练库及新复制的素材，保留已验证原包。源库和源对象始终不改，不需要“恢复旧库”。新版正式承接用户新操作后，不得整库恢复或按用户级联删除；需以导入批次及新增业务关系复核，制定另一项受控回退任务。验收后的导出包按批准的访问和保留期限管理，不对旧资产做清理操作。
