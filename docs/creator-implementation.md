## Task 1: Delegated account authorization

Implement the OAuth and device authorization foundation in apps/api-core/src/creator-auth, related tests, packages/database schema and one additive migration. Wire module/main/common behavior as needed. Also implement simple Chinese consent, device-confirmation and connected-client pages in apps/web (/creator/authorize, /creator/device, /account/connections), using existing auth session; public install page comes later. Do not change creator book/media/courses business logic, deployment or packages beyond necessary dependencies.

Use OAuth 2.1 authorization code with required S256 PKCE for public clients, resource indicators bound at authorization, exact redirect URI validation (HTTPS or localhost native loopback), safe dynamic client registration, state roundtrip. Approval must require existing account login and CSRF/origin protection; never grant from a GET. Browser consent remains on main site and only opaque expiring transaction identifiers in URLs. Avoid accepting arbitrary client metadata URLs or fetching them. DCR must have quotas/limits; names untrusted. Explicit consent scopes: creator:read creator:write creator:submit. No admin/delete/generation powers. An auth principal includes userId, grantId, clientId, scopes, audience.

Issuer routes exposed internally /api/creator-auth/oauth/{authorize,token,register,revoke,device}; metadata at /api/creator-auth/metadata and /api/creator-auth/resource-metadata?resource=mcp|api for nginx mapping. Authorize GET validates then redirects to main-site consent with transaction ID. Token/revoke/register/device use protocol responses without business envelope and no-store headers. Protected resource unauthorized helper must advertise metadata location. Same-origin browser endpoints /api/creator-auth/requests/:id (read + POST decision), /api/creator-auth/device/lookup and /api/creator-auth/device/decision; /api/creator-auth/connections list and DELETE :id. Prefer unique operation names to avoid OAuth/device route collision.

Support RFC8628 device grant for bundled helper. Device verification URI at main site; minimum poll interval enforced; pending, denied, expired and slow_down responses; consume once, random high entropy codes, human code brute force limits and displayed client/scopes. Browser user authenticates and confirms; helper never asks password. Access expires in 15 minutes, refresh rotates and expires in 30 days, grants revocable. Store token/code hashes, not bearer secrets. Token refresh replay revokes family, same transaction atomic consume. Each request validates active user/grant/audience/scopes, refresh preserves allowed scopes and resource. Export CreatorAuthService.authenticateBearer(request, audience, requiredScopes) and its principal type for downstream tasks; return internal userId only from validated principal. DB concurrency must be safe with row/advisory locking/conditional consume. Add aud-specific grant token issuance; no MCP token accepted by direct Creator API.

Tests: real DB code+PKCE, wrong client/redirect/resource/verifier, code replay/expiry, consent authentication/CSRF, device pending/interval/deny/approve/expiry, refresh rotation/replay/revoke, foreign grant revoke rejected, inactive user, scope escalation. Test compiled Nest wiring if tsx metadata limitations. Run db:generate/database build/API typecheck/web typecheck and focused tests with test env only; report exact commands and RED/GREEN. No production seed. Add interfaces documentation for next task in report.
